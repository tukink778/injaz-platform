# تشغيل INJAZ على PostgreSQL (Neon) + Render

## 1) كيف يختار النظام القاعدة
| الحالة | القاعدة |
|---|---|
| `DATABASE_URL` غير مضبوط | SQLite محلية في `data/injaz.db` (كما كان) |
| `DATABASE_URL=postgresql://...` | PostgreSQL (يُقبل `postgres://` ويُحوَّل). الاتصال عبر `psycopg 3` + `psycopg_pool` |

الواجهة `db()` و`connect()` كما هي. الفروق تُعالَج داخل `app/db.py`: تحويل `?` إلى `%s`، `LIKE` غير الحساس للحالة، هوية تلقائية `GENERATED ... AS IDENTITY`، `RETURNING id` بدل `lastrowid`، معاملات متداخلة عبر SAVEPOINT، قفل استشاري لسلسلة التدقيق وللهجرات، `c.columns()` بدل `PRAGMA`، `c.month_of_epoch()` بدل `strftime`.
الأسرار: رابط الاتصال لا يُطبع ولا يدخل رسائل الأخطاء (تُحذف كلمة المرور منها).

## 2) إعداد Neon
1. أنشئ مشروعاً وقاعدة في Neon. من **Connect** انسخ الرابط. استخدم رابط **Pooled** (يحوي `-pooler` في اسم المضيف) للتطبيق. الرابط يحوي `sslmode=require` وهو مطلوب.
2. وفق وثائق Neon: خلف PgBouncer لا تعمل أقفال الجلسة ولا `SET` الدائم؛ النظام لا يستخدمها (الأقفال على مستوى المعاملة فقط، و`prepare_threshold=None`). لذلك **لا تضبط `INJAZ_DB_SCHEMA` مع رابط -pooler** (هذا المتغير للاختبار المحلي فقط).
3. Neon قد «ينام» عند الخمول: أول اتصال قد يتأخر ثوانٍ؛ المهلة `INJAZ_DB_CONNECT_WAIT=30`، والمجمّع يعيد الاتصال تلقائياً ويتحقق من صلاحية الاتصال قبل تسليمه.

## 3) إعداد Render
1. اربط المستودع (GitHub) كـ **Web Service** بنوع **Docker**. لا ترفع `.env` ولا `data/` (مستثناة في `.gitignore`).
2. المتغيرات (Environment) — كلها تُدخل في لوحة Render لا في الملفات:
| المتغير | القيمة |
|---|---|
| `DATABASE_URL` | رابط Neon (pooled) — سرّي |
| `INJAZ_MASTER_KEY` | المفتاح الرئيسي — سرّي ودائم (القسم 4) |
| `INJAZ_BASE_URL` | `https://<اسم-خدمتك>.onrender.com` (أو دومينك) |
| `INJAZ_ALLOWED_HOSTS` | المضيف نفسه دون بروتوكول |
| `INJAZ_HTTPS` | `1` |
| `INJAZ_BEHIND_PROXY` / `INJAZ_TRUSTED_PROXY` / `INJAZ_PROXY_COUNT` | `1` / `*` / `1` |
| `INJAZ_DB_POOL_MAX` | `8` (مناسب لنسخة واحدة) |
3. **Health Check Path**: `/healthz` (يعيد 200 مع `{"status":"ok","db":"postgres"}` أو 503 دون أي سرّ).
4. المنفذ: Render يمرّر `PORT` (الافتراضي 10000) والتطبيق يستمع على `0.0.0.0:$PORT` تلقائياً.
5. الهجرات: تُطبَّق تلقائياً عند بدء التشغيل (مرة واحدة لكل هجرة، داخل معاملة، وبقفل يمنع تشغيلها من نسختين معاً). لا شيء يدوي.
6. **إنشاء حساب المشرف** (مرة واحدة، يدوياً — لا يُنفَّذ تلقائياً): `python manage.py init` من Shell الخدمة في Render إن توفّر لخطتك، أو محلياً بعد ضبط `DATABASE_URL` و`INJAZ_MASTER_KEY` في جلسة الطرفية فقط (لا في ملف) نحو قاعدة Neon نفسها.
7. ملف `render.yaml` اختياري ويحوي القيم غير السرّية.

## 4) مفتاح التشفير (الأهم)
- في وضع PostgreSQL **يرفض النظام الإقلاع** بلا `INJAZ_MASTER_KEY` ولا يولّد مفتاحاً جديداً أبداً (حتى لا يضيع كل شيء مع قرص Render المؤقت).
- ولّده **مرة واحدة**: `python -c "import secrets,base64;print(base64.urlsafe_b64encode(secrets.token_bytes(32)).decode())"` ثم: (أ) ضعه في Render ← Environment ← `INJAZ_MASTER_KEY`، (ب) احفظ نسخة في مدير كلمات مرور أو خزنة خارج Render وGitHub.
- إن كانت لديك بيانات مشفّرة سابقة فاستخدم مفتاحها الأصلي نفسه (من `data/.keys` ← الحقل `master`، أو من `INJAZ_MASTER_KEY` القديم).
- **حارس المفتاح:** عند أول إقلاع تُخزَّن بصمة HMAC للمفتاح في القاعدة (لا تكشفه). أي إقلاع لاحق بمفتاح مختلف يتوقف برسالة واضحة قبل أن يكتب أي شيء، فلا يمكن إتلاف البيانات بنشر خاطئ. وإن وُجدت بيانات بلا بصمة (قاعدة قديمة) يُتحقق بفك تشفير سجل حقيقي قبل الوثوق بالمفتاح.
- تدوير المفتاح غير مدعوم حالياً (فقدانه = فقدان القدرة على قراءة الأسماء والبريد والأرقام الجامعية وملفات PDF).

## 5) الملفات وملفات PDF (ليست في القاعدة)
- PDF المشفّرة تُحفظ في `INJAZ_DATA_DIR/certs/*.pdf.enc` (المسار والأسماء بلا تغيير) عبر طبقة `app/storage.py` (كتابة ذرّية). القاعدة تحفظ اسم الملف فقط.
- **قرص Render افتراضياً مؤقت:** يُمسح عند كل نشر/إعادة تشغيل. على الخطة المجانية ستفقد الـPDF (تبقى سجلات القاعدة، ويمكن إعادة توليدها). للحفظ الدائم: أضف **Persistent Disk** (خطة مدفوعة) وركّبه على `/app/data`، أو انتقل لاحقاً إلى Object Storage بإضافة صنف جديد في `app/storage.py` (`save/load/exists`) واختياره عبر `INJAZ_STORAGE_BACKEND`؛ المحتوى مشفّر مسبقاً فلا يلزم تشفير إضافي.
- تنبيه: الحاوية تعمل بمستخدم غير root (uid 10001). إن لم يكن القرص المركَّب قابلاً للكتابة لهذا المستخدم فتحقق من ذلك عند أول نشر (لم أستطع اختباره هنا).
- المجلدات `staging` و`tmp` و`outbox` مؤقتة بطبيعتها (الاستيراد المعلّق، ملفات التوليد، رسائل وضع الاختبار). `backups` يجب نسخه خارج الخادم.

## 6) النسخ الاحتياطي والاستعادة
- `python manage.py backup`: على PostgreSQL ينتج zip فيه `pgdump.json` (نسخة منطقية لكل الجداول، لا تحتاج `pg_dump`) + ملفات PDF + الأصول. **لا يتضمن المفتاح.**
- `python manage.py restore FILE.zip`: ترفض إن كانت القاعدة غير فارغة إلا مع `--force`، وتُزامن عدّادات الهوية بعد الاستعادة.
- ينصح أيضاً بميزة Neon (Point-in-Time Restore/Branching) لحماية القاعدة نفسها.

## 7) ترحيل بياناتك الحالية من SQLite إلى Neon
**لم يُنفَّذ أي ترحيل.** الأداة الحالية لا تحوّل نسخة SQLite تلقائياً إلى PostgreSQL (الاستعادة ترفضها عمداً). عند موافقتك نضيف أمر ترحيل مختبراً (`sqlite → postgres` بالمفتاح نفسه) ونجري تجربة جافة قبل أي كتابة فعلية.

## 8) التشغيل المحلي
- SQLite: كما سبق (`python manage.py init` ثم `python wsgi.py`) بلا `DATABASE_URL`.
- PostgreSQL محلياً (للتجربة): `export DATABASE_URL=postgresql://user:pass@localhost:5432/injaz` و`export INJAZ_MASTER_KEY=...` ثم `python wsgi.py`.
- الاختبارات: `python tests/run_all.py` (SQLite) · `DATABASE_URL=postgresql://...localhost.../test_db python tests/run_all.py` (PostgreSQL؛ يرفض غير المحلي ما لم تمرّر `--i-know-this-is-a-test-db`، وكل اختبار في schema مؤقت يُحذف بعده).

## 9) ما لم يُختبر هنا
Neon وRender أنفسهما (لا وصول لهما من بيئة التطوير). اختُبر على PostgreSQL 16 محلي بالتطابق نفسه من حيث السائق والأوامر. يجب التحقق عند أول نشر من: اتصال Neon عبر -pooler، صلاحية الكتابة على القرص الدائم، وأن آخر عنوان في `X-Forwarded-For` هو عنوان العميل لدى Render (يتحكم به `INJAZ_PROXY_COUNT`؛ يحدد تحديد معدل الدخول بحسب العنوان).
